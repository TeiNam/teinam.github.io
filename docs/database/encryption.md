## 1. 암호화의 필요성

- 개인정보 유출은 신원 도용, 금전적 피해, 기업 평판 훼손으로 직결되므로 암호화가 필수적입니다.
- 암호화는 데이터가 유출되더라도 복호화 키 없이는 정보가 해독되지 않도록 보장하여 2차 피해를 예방합니다.
- 국내외 개인정보 보호 법·제도는 민감정보 저장 시 암호화를 의무화하고 있어 법적 리스크를 회피할 수 있습니다.

## 2. 개요

### 2.1 적용 범위

- 이 가이드는 공공·민간기관의 관계형 및 NoSQL 데이터베이스에 저장되는 모든 개인정보 컬럼을 대상으로 합니다.
- 적용 대상 개인정보에는 주민등록번호, 여권번호, 연락처, 결제정보, 바이오 정보 등이 포함됩니다.

### 2.2 기본 원칙

- 기밀성: 암호화된 데이터는 키 없이는 절대 복호화 불가
- 무결성: 암호모듈 검증으로 알고리즘·구현 적합성 보장
- 가용성: 암호화 구현 시 성능·운영 편의성 고려

## 3. 목적

1. 데이터베이스 내 개인정보의 기밀성과 무결성 확보
2. 국가표준 및 법적 요구사항(전자정부법, 개인정보보호법 등) 충족
3. 보안 사고 발생 시 2차 피해 최소화 및 사용자 신뢰도 제고

## 4. 감사 기준점

암호화는 "했다/안 했다"가 아니라 **어느 기준의 몇 번 항목을 무엇으로 증명하는가**로 평가된다. 실무에서 마주치는 기준은 넷이다.

| 기준 | 소관 | 암호화 관련 항목 | 성격 |
| --- | --- | --- | --- |
| 개인정보 보호법 | 개인정보보호위원회 | 제24조의2(주민등록번호 암호화), 제29조(안전조치의무) | 법률 |
| 개인정보의 안전성 확보조치 기준 | 개인정보보호위원회 | 제7조(개인정보의 암호화) | 고시 |
| ISMS-P 인증기준 | 과기정통부·개인정보보호위원회, 심사 KISA | 2.7.1 암호정책 적용, 2.7.2 암호키 관리 | 인증 |
| 암호모듈 검증(KCMVP) | 국가정보원 | 검증필 암호모듈 사용 | 공공 조달 요건 |

DB 를 다루면 암호화(2.7) 만으로 끝나지 않는다. 심사에서 같이 딸려오는 항목:

- **2.6.4 데이터베이스 접근** — 개인정보를 담은 테이블에 누가 접근할 수 있는지, 계정이 분리돼 있는지
- **2.9.4 로그 및 접속기록 관리 / 2.9.5 점검** — 복호화 조회를 포함한 접속기록이 남고 점검되는지
- **3.x 개인정보 처리단계별 요구사항** — 수집·보유·파기 단계에서 암호화가 유지되는지

### 4.1 무엇을 반드시 암호화해야 하나

법정 의무 대상과 위험도 판단 대상은 다르다. 섞으면 감사에서 근거를 못 댄다.

| 구분 | 대상 | 방식 |
| --- | --- | --- |
| 규모·환경 무관 의무 | 주민등록번호 | 저장 시 암호화 (법 제24조의2 제2항) |
| 의무 | 비밀번호 | **복호화 불가능한 일방향 암호화** |
| 의무 | 바이오정보, 그 외 고유식별정보(여권·운전면허·외국인등록번호) | 저장·전송 시 암호화 |
| 위험도 기반 | 그 외 개인정보 | 개인정보 영향평가 또는 위험도 분석 결과에 따라 결정하고 **판단 근거를 문서로 남긴다** |

> **IMPORTANT** — 위험도 기반 항목은 "안 했다"가 아니라 "판단했다"를 증명해야 한다
>
> 암호화하지 않기로 했다면 그 결정을 내린 분석 문서와 승인 기록이 곧 증빙이다. 아무 기록 없이 평문이면 판단 자체가 없었던 것으로 본다.

## 5. 암호모듈 검증 제도(KCMVP)

- 검증기준: KS X ISO/IEC 19790:2015(보안요구사항), KS X ISO/IEC 24759:2015(시험요구사항) 기반
- 검증필 암호모듈: 시험기관·검증기관 심의를 통과한 모듈에 검증번호 부여
- 제품 도입 요건: CC인증 또는 보안기능 확인서 취득, 검증필 모듈 탑재 필수

## 6. 암호화 적용 방안

### 6.1 컬럼 수준 암호화

- 대칭키 암호화: 주민등록번호·카드정보 등 민감 컬럼은 AES-256 권장
- 키 식별자: 각 암호화 컬럼에 **키 버전**을 함께 저장한다. 키를 회전해도 예전 값을 복호화할 수 있어야 한다
- 일방향 해시: 비밀번호는 **연산 비용이 있는 KDF** 로 저장한다 — Argon2id, bcrypt, scrypt, PBKDF2

> **WARNING** — SHA-256/SHA-3 단독은 비밀번호 저장에 쓰지 않는다
>
> 범용 해시는 빠른 것이 목적이라 GPU 로 초당 수십억 회 시도할 수 있다. 비밀번호에는 반복 횟수·메모리 비용을 조절할 수 있는 KDF 를 쓰고, 솔트는 계정마다 다르게 생성한다. 범용 해시는 가명처리용 식별자 치환처럼 **속도가 필요한 용도**에만 쓴다.



### 6.2 전송 구간 암호화

- DB 연결 시 SSL/TLS 사용으로 중간자 공격 방지
- 공개키 인프라(PKI) 적용 권장

### 6.3 암호화 계층 선택

어디서 암호화하느냐에 따라 막을 수 있는 위협이 다르다. 감사에서 "왜 이 방식인가"를 묻는 지점이다.

| 계층 | 막는 것 | 못 막는 것 | 검색 |
| --- | --- | --- | --- |
| 저장장치·TDE | 디스크·백업 파일 탈취 | DB 에 로그인한 계정의 조회, SQL 인젝션 | 영향 없음 |
| DB 컬럼 암호화 | 파일 수준 접근, 일부 권한 우회 | DB 가 키를 알고 있어 DBA 는 복호화 가능 | 제약 발생 |
| 애플리케이션 암호화 | DBA 를 포함한 DB 접근자 전원 | 애플리케이션 서버 침해 | 크게 제약 |

TDE 만 켜놓고 "암호화했다"고 하는 경우가 흔한데, TDE 는 **백업 테이프를 잃어버렸을 때**를 막는 것이지 계정 탈취를 막지 않는다. 주민등록번호처럼 법정 의무 대상은 컬럼 또는 애플리케이션 계층에서 처리한다.

## 7. 키 관리

- HSM 활용: 암호키 저장·생성·백업·교체 운영
- 라이프사이클 관리: 키 생성→배포→회전→폐기 절차 문서화
- 접근 통제: RBAC/MFA 기반 키 사용 권한 제한

## 8. 성능 및 운영 고려사항

- 오버헤드 평가: CPU·I/O 영향 측정 후 캐싱·배치 암호화 설계
- 검색이 필요한 암호화 컬럼은 **블라인드 인덱스**를 따로 둔다. 원문의 HMAC 값을 별도 컬럼에 저장하고 그 컬럼에 인덱스를 건다. 동등 비교(`WHERE email_idx = HMAC(?)`)만 가능하고 `LIKE`·범위 검색은 안 된다
- 같은 평문이 항상 같은 암호문이 되는 결정적 암호화는 인덱스를 쓸 수 있지만 **값의 분포가 드러난다.** 성별·등급처럼 카디널리티가 낮은 컬럼에 쓰면 사실상 평문이다
- 부분 검색이 꼭 필요하면 암호화 대신 가명처리·범주화로 요구사항을 바꿀 수 있는지 먼저 검토한다
- 모니터링: 암호모듈 호출 로그 SIEM 연동, 이상 징후 탐지·알림

## 9. 컴플라이언스 및 감사

- 연 1회 이상 내부 관리계획 이행 점검
- 외부 보안 적합성 검증(국정원·KISA) 보고서 보관
- 법령 개정 시 가이드라인 업데이트 프로세스 수립

## 10. 감사 증빙

심사·감사에서 요구받는 것은 설정 화면이 아니라 **기록**이다. 사후에 만들 수 없으므로 운영 중에 남긴다.

| 항목 | 남겨야 하는 것 |
| --- | --- |
| 암호화 대상 선정 | 개인정보 항목별 암호화 여부와 그 판단 근거, 승인 기록 |
| 알고리즘·키 길이 | 적용 알고리즘 목록과 검증필 암호모듈 사용 여부 |
| 키 관리 | 키 생성·배포·회전·폐기 이력, 키 접근 권한자 목록과 변경 이력 |
| 키 회전 | 마지막 회전 일시, 재암호화 대상 범위와 완료 확인 |
| 복호화 접근 | 누가 언제 어떤 컬럼을 복호화 조회했는지 (접속기록) |
| 이행 점검 | 연 1회 이상 내부관리계획 이행 점검 결과 |

### 10.1 키 회전 시 재암호화

키를 바꾸면 기존 데이터를 다시 암호화해야 한다. 운영 중인 테이블에서는 한 번에 처리할 수 없다.

1. 새 키를 발급하고 **키 버전**을 부여한다. 신규 쓰기는 새 키로 한다
2. 기존 행을 배치로 읽어 복호화 후 새 키로 재암호화한다. 키 버전 컬럼으로 진행 상황을 추적한다
3. 옛 키 버전을 가진 행이 0 이 되면 옛 키를 폐기한다. **그전에 폐기하면 복구 불가능하다**
4. 백업본은 옛 키로 암호화돼 있다. 백업 보관 기간이 지날 때까지 옛 키를 폐기 대상이 아닌 **보관 대상**으로 분리한다

### 10.1 키 회전 시 재암호화

키를 바꾸면 기존 데이터를 다시 암호화해야 한다. 운영 중인 테이블에서는 한 번에 처리할 수 없다.

1. 새 키를 발급하고 **키 버전**을 부여한다. 신규 쓰기는 새 키로 한다
2. 기존 행을 배치로 읽어 복호화 후 새 키로 재암호화한다. 키 버전 컬럼으로 진행 상황을 추적한다
3. 옛 키 버전을 가진 행이 0 이 되면 옛 키를 폐기한다. **그전에 폐기하면 복구 불가능하다**
4. 백업본은 옛 키로 암호화돼 있다. 백업 보관 기간이 지날 때까지 옛 키를 폐기 대상이 아닌 **보관 대상**으로 분리한다

## 요약

- 암호화는 "적용 여부"가 아니라 **어느 기준의 어떤 항목을 무엇으로 증명하는가**로 평가된다 (4장)
- 주민등록번호·비밀번호·바이오정보·고유식별정보는 법정 의무 대상이고, 나머지는 **위험도 판단과 그 근거 문서**가 증빙이다 (4.1)
- 비밀번호는 범용 해시가 아니라 연산 비용이 있는 KDF 로 저장한다 (6.1)
- TDE 는 저장매체 탈취를 막을 뿐 계정 탈취를 막지 않는다. 법정 의무 대상은 컬럼 또는 애플리케이션 계층에서 처리한다 (6.3)
- 암호화 컬럼 검색은 블라인드 인덱스로 동등 비교만 가능하다. 부분 검색이 필요하면 요구사항 자체를 재검토한다 (8장)
- 키 회전은 키 버전 컬럼으로 진행 상황을 추적하고, 백업 보관 기간이 지나기 전에는 옛 키를 폐기하지 않는다 (10.1)
